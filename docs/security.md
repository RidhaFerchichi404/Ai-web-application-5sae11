# Security

Status: Planned. The controls below are requirements for later phases, especially Phase 5 and Phase 10. They are not implemented.

The application is a local personal assistant. That does not remove the need to treat uploads and configuration carefully. A file the user uploads is data, not code.

## File type validation

The API will accept only PDF, DOCX, TXT, and Markdown. The check will use the extension and the detected content type. A renamed executable will be rejected.

## File size limits

`MAX_FILE_SIZE_MB` caps each upload. The example value is 25. Requests over the limit will be rejected before the file is written in full, as far as the server stack allows. The exact streaming limit will be set in Phase 5.

## Filename sanitization

Display names will drop path separators and control characters. The stored name will be generated by the server. The original name will not be used as a filesystem path.

## Path traversal prevention

Reads and deletes will resolve the stored path and require that it stay inside `UPLOAD_DIRECTORY`. A `stored_filename` that contains `..` or an absolute path will be rejected. User input will never be concatenated into a path without that check.

## Input validation

Pydantic schemas will validate JSON bodies, ids, and query parameters. Unknown fields will not be passed into SQL. Role values, document status values, and model names will be checked before use.

## Environment variables

Secrets and machine-specific settings live in the environment, loaded from a local `.env` that is gitignored. `.env.example` contains placeholders only. The repository will not contain database passwords or API tokens.

There is no cloud language-model key in the planned configuration, because inference stays on Ollama.

## Database credentials

`DATABASE_URL` will carry the MySQL user and password. Logs and error responses will not print that URL. The MySQL account used by the app should have rights only on `local_ai_assistant`, not on other databases. That account setup is an operator step, documented here so Phase 2 does not use a privileged account by habit.

## API validation

Routes will reject malformed ids, empty chat messages, and uploads that fail the file rules. Conversation and document ids that do not exist will return a not-found response without revealing whether a row exists for a different owner once ownership checks exist. Until authentication exists, the app is a single local user and this cross-user case does not arise. The queries will still be written with `user_id` so a later login decision does not require a rewrite.

## No execution of uploaded files

The server will not shell out to uploaded files, will not `import` them, and will not render them as active content. PDF and DOCX libraries will be used to read text only.

## Error sanitization

Clients will receive a short message and an error code. Stack traces, SQL, absolute paths, and Ollama request bodies will stay in server logs.

## Local file access restrictions

Backend file access for user content is limited to `UPLOAD_DIRECTORY`. The process will not accept a client-supplied filesystem path to read arbitrary host files.

## Configuration security

Phase 10 reviews logging, dependency pins, and startup failures on missing settings. Docker definitions, when they exist, will not bake secrets into images. They are not written yet.

## Authentication

Not scheduled in Phases 1–10. Do not add a password store or a session cookie as an undocumented extra. A future login feature needs its own decision-log entry.
